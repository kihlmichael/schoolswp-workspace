- Faits constates :
  - Les trois modes de creation passent tous par un seul endpoint POST /v3/avatars, distingues par le champ `type` : "Three creation modes all go through POST /v3/avatars - distinguished by the `type` field." (https://developers.heygen.com/docs/create-avatar)
  - Le champ `type` est le discriminateur de l'union, avec mapping vers 3 schemas : "discriminator: mapping: digital_twin ... photo ... prompt ... propertyName: type" (https://developers.heygen.com/reference/create-avatar.md)
  - Mode digital_twin - cree un avatar a partir d'une video, le locuteur devient un jumeau numerique reutilisable : "Create an avatar from video footage. The speaker in the video becomes a reusable digital twin." Champs requis : `type` (const "digital_twin"), `name`, `file` ; `avatar_group_id` optionnel (https://developers.heygen.com/docs/create-avatar ; https://developers.heygen.com/reference/create-avatar.md)
  - Mode photo - cree un avatar a partir d'une seule photo, sans enregistrement video : "Create an avatar from a single photo. Quick to set up - no video recording needed." Champs requis : `type` (const "photo"), `name`, `file` ; `avatar_group_id` optionnel (https://developers.heygen.com/docs/create-avatar ; https://developers.heygen.com/reference/create-avatar.md)
  - Mode prompt - genere un avatar AI entierement synthetique a partir d'un texte, via le pipeline Tokyo : "Generate an entirely new AI avatar from a text description. ... the Tokyo pipeline creates it." et "The avatar is fully synthetic - no real person is depicted." Champs requis : `type` (const "prompt"), `name`, `prompt` (max 1000 chars) ; `avatar_group_id` et `reference_images` (max 3) optionnels (https://developers.heygen.com/docs/create-avatar ; https://developers.heygen.com/reference/create-avatar.md)
  - Le champ `type` est documente comme une constante par mode : "type: const: digital_twin", "type: const: photo", "type: const: prompt" (https://developers.heygen.com/reference/create-avatar.md)
  - Flux de consentement - qui en a besoin : seuls les avatars digital_twin requierent un consentement : "Consent is only required for digital twin avatars (`type: \"digital_twin\"`). Photo avatars and prompt-to-avatar characters do not require consent." (https://developers.heygen.com/docs/create-avatar)
  - L'endpoint de consentement initie le flux et renvoie une URL a visiter par le sujet : "Initiates the consent flow for an avatar group and returns a URL for the user to complete approval in their browser. Required before a private avatar can be used for video generation." (POST /v3/avatars/{group_id}/consent) (https://developers.heygen.com/reference/create-avatar-consent.md)
  - Le corps de requete consentement accepte `reroute_url` (optionnel, defaut = page de fin HeyGen) et `consent_text` (optionnel, premium Enterprise) : "Callback URL where the user is redirected after completing consent. Defaults to HeyGen's consent completion page." et "Custom consent text ... Available as a premium option for select Enterprise customers" (https://developers.heygen.com/reference/create-avatar-consent.md)
  - La reponse consentement renvoie `avatar_group` et `url` (URL de la page de consentement) : "url: description: URL to the consent page." champs requis : avatar_group, url (https://developers.heygen.com/reference/create-avatar-consent.md)
  - Pour savoir quand le consentement est complete, verifier `consent_status` via GET /v3/avatars/{group_id} : "Check `consent_status` on the avatar group via GET /v3/avatars/{group_id} to know when consent is complete." (https://developers.heygen.com/docs/create-avatar)
  - Groupes et looks : un avatar group est une identite de personnage, chaque groupe peut avoir plusieurs looks : "An avatar group is a character identity (e.g. 'Sarah'). Each group can have multiple looks - different outfits, poses, or styles." (https://developers.heygen.com/docs/create-avatar)
  - Pour creer une video, on passe un ID de look (pas un ID de groupe) comme `avatar_id` : "When creating a video, you pass a look ID (not a group ID) as the `avatar_id`." (https://developers.heygen.com/docs/create-avatar)
  - On peut generer de nouveaux looks pour un avatar existant via `type: "prompt"` + `avatar_group_id` ; un des looks du groupe sert de base : "If set, the generated look is added to this existing avatar group and one of the group's looks is used as the base that conditions the generation." (https://developers.heygen.com/docs/create-avatar)
  - Champ de reponse `avatar_type` : valeurs "digital_twin", "photo_avatar", ou "studio_avatar" : "avatar_item.avatar_type | string | \"digital_twin\", \"photo_avatar\", or \"studio_avatar\"." et enum AvatarLookType : studio_avatar, digital_twin, photo_avatar (https://developers.heygen.com/docs/create-avatar ; https://developers.heygen.com/reference/create-avatar.md)
  - Champ de reponse `supported_api_engines` : liste des moteurs compatibles pour POST /v3/videos : "Engine values this look supports for POST /v3/videos." exemples cites : "avatar_v", "avatar_iv" (reference) et "avatar_4_quality", "avatar_4_turbo" (exemple docs) (https://developers.heygen.com/reference/create-avatar.md ; https://developers.heygen.com/docs/create-avatar)
  - Champ de reponse `consent_status` : "The status of consent for the group. None means consent is not required." ; dans la reponse de creation : "null for photo and prompt avatars. Digital twins may require consent" (https://developers.heygen.com/reference/create-avatar.md ; https://developers.heygen.com/docs/create-avatar)
  - Statut d'avatar (enum AvatarStatus) : processing, pending_consent, failed, completed : "enum: processing, pending_consent, failed, completed" (https://developers.heygen.com/reference/create-avatar.md)
  - Reponse de creation : champ `avatar_item.id` = ID du look a passer comme `avatar_id` a POST /v3/videos : "The look ID - pass this as `avatar_id` to POST /v3/videos" (https://developers.heygen.com/docs/create-avatar)
  - Formats de fichier acceptes pour `file` : url, asset_id (depuis POST /v3/assets), ou base64 : "{ \"type\": \"url\", \"url\": \"...\" }, { \"type\": \"asset_id\", \"asset_id\": \"...\" } ... or { \"type\": \"base64\", \"media_type\": \"video/mp4\", \"data\": \"...\" }" (https://developers.heygen.com/docs/create-avatar)
  - L'entrainement de l'avatar est asynchrone : "Avatar training is asynchronous." (https://developers.heygen.com/reference/create-avatar.md)

  - Endpoint de gestion des webhooks : "Base path: `https://api.heygen.com/v3/webhooks/endpoints`". Operations CRUD documentees : Create (`POST`), List (`GET`), Update (`PATCH`), Delete (`DELETE`), Rotate Signing Secret (`POST .../rotate-secret`). (https://developers.heygen.com/docs/webhooks)
  - Creation d'endpoint et evenements : champ `events` optionnel, exemple `["avatar_video.success", "avatar_video.fail"]`. "Omit or set to `null` to receive all events." (https://developers.heygen.com/docs/webhooks)
  - Verification des payloads obligatoire : "Always verify before trusting the payload - without verification, anyone who learns your URL can forge events. HeyGen signs the raw request body with HMAC-SHA256 using the endpoint `secret`". Headers fournis : `Heygen-Signature`, `Heygen-Timestamp`, `Heygen-Event-Id`. (https://developers.heygen.com/docs/webhooks)
  - Contraintes de livraison (limites pour l'automatisation) : "Success criteria: respond with `2xx` within 10 seconds. Slow handlers will be timed out and retried." ; "Retries: failed deliveries are retried with exponential backoff for up to 24 hours." ; de-duplication via `Heygen-Event-Id` ; rejeter les livraisons dont `Heygen-Timestamp` depasse environ 5 minutes. (https://developers.heygen.com/docs/webhooks)
  - Alternative au webhook persistant (callbacks one-off) : "If you don't need a persistent webhook endpoint, pass a `callback_url` directly when creating a video".   - Role du MCP (chemin recommande pour un agent) : "If `mcp__heygen__*` tools are visible in your toolset, the user is already connected to the HeyGen Remote MCP over OAuth. (https://developers.heygen.com/docs/for-ai-agents)
  - Ladder de detection auth pour un agent (ordre recommande) : utiliser le premier qui repond, sans les combiner - 1) MCP server ("fastest path"), 2) HeyGen CLI, 3) Raw API ("last resort"). "Use the first one that resolves - don't combine them." (https://developers.heygen.com/docs/for-ai-agents)
  - Workflow de generation recommande : "MCP: call `mcp__heygen__create_video_from_avatar` or the Video Agent variant." ; "API: `POST /v3/video-agents` with `{ \"prompt\": \"<prompt>\" }`, then poll `GET /v3/videos/{video_id}` until `status` is `completed` (1-5 minutes). In production, pass a `callback_url` and skip polling." (https://developers.heygen.com/docs/for-ai-agents)
  - Limites de polling pour l'automatisation : "Polling has a ceiling. Most videos complete in 1-5 minutes. Use exponential backoff, respect `Retry-After` on `429`s (Usage Limits), and prefer `callback_url` in production." (https://developers.heygen.com/docs/for-ai-agents)
